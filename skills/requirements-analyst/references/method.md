# 从问题到可验收需求

以下是对用户提供课程方法的重新整理，来源索引见 [学习来源](sources.md)。

1. 问题发现：记录真实痛点及发生情境，频率与影响有证据时再评分；不要编造调研数据。
2. JTBD：描述“某类用户在某情境下要完成某任务，以获得某结果”，同时记录现有替代方式及不足。功能任务和情感诉求可分别记录；推测的动机必须标为假设。
3. 风险预演：考虑需求、技术、使用场景和使用习惯中的失败原因。将重要风险对应到预防措施、失败信号与后续动作。负责人、时间、成本未知时不要代填。
4. MVP 减法：逐项询问没有它能否完成核心任务、能否验证核心假设、首次使用是否需要。形成 P0/P1/P2 与本期不做清单。数量建议不应压过用户实际范围。
5. 用户流程：从首次使用到核心任务完成，记录动作、系统反馈、异常与恢复。只有必要时才扩展画像和长期旅程。
6. 场景约束：记录本地或云端、数据去向、覆盖保护、权限、性能等实际约束。不要将课程中面向新手的选题建议变成对所有项目的一律禁止。
7. PRD：将上述产出落到八个主体字段，再增加来源、待确认项和验收追踪。
8. 自查与复述：检查歧义、缺失边界与范围外功能，用用户能理解的话复述需求，并明确仍需用户决定的部分。

## 事实、建议与未决事项

用户明确提出的规则可进入已知需求。分析者提出的方案必须注明建议，不能写成已确认事实。未知的技术栈、预算或性能指标以“待确认”保留；存在影响 P0 的待确认项时，文档应维持草稿状态。

## 可验收性

不要只写“导出正常”。应写清前置条件、动作与结果，例如“已有两条有效记录时，选择导出后得到含两条数据的文件，原记录保持不变”。成功、失败和边界都应依据真实业务契约定义。
