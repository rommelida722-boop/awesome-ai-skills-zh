# 示例、适用边界与人工评测

完整契约见仓库 examples/requirements/tasks.json，演示产物见同目录 requirements.md。案例全部虚构，不来自真实用户访谈。

JSON 根对象包含项目名称、一句话描述、目标用户、要解决的问题；核心功能和成功标准为非空对象数组；不做的功能、用户流程、技术约束、风险、待确认事项为文本数组。用户流程不能为空，其余数组可为空，但空数组不证明已分析充分。未知事实应写入待确认事项，不用空字符串填充。

每个功能含唯一 F-001 格式编号、名称、P0/P1/P2 优先级、来源、输入、规则、输出。每条成功标准含唯一 A-001 格式编号、功能编号、前置条件、动作、预期结果。每个功能都必须关联至少一条验收项。

成功：完整契约导出可追踪需求文档。失败：缺用户、空文本、重复编号、孤立引用、无验收功能或覆盖已有输出时拒绝，CLI 返回 2。脚本不会验证来源是否真实、指标是否合理或自然语言是否矛盾。

## 可复现人工评测

在三个新聊天中分别调用本 Skill；这些是待执行的行为案例，不是已通过的自动化结果。

| 输入 | 应观察到的行为 | 不合格表现 |
| --- | --- | --- |
| 我是实训学生，要做本地任务清单；能添加和完成，不要登录和联网。 | 提取用户与 JTBD；两项核心功能；保留离线约束；为正常和非法输入定义验收；存储待确认 | 擅自加入云同步、支付或声称已确认存储方案 |
| 帮我写一个智能平台的需求分析。 | 先整理已知内容，优先询问用户、核心任务及成功定义；保持草稿 | 编造用户数量、调研结果、并发指标或输出已确认 PRD |
| 访谈甲要求完全离线；访谈乙要求实时跨设备同步。 | 保留两条来源，指出冲突与受影响范围，列出待决定选项 | 悄悄忽略一方，或者宣称两者无需取舍即可满足 |

质量标准：来源可追踪、未决项显式列出、不扩张范围、验收能判定通过或失败。脚本通过不等于这些语义标准通过。
